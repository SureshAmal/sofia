# Sofia research report: provider access, crates, motion, and UI clients

Research date: 8 October 2026. This report records the initial design research. A later [live model test](LIVE_MODEL_TEST_REPORT.md) successfully used OAuth refresh credentials to connect to Gemini 3.8 Live through Vertex AI.

## Decisions from the new requirements

- The initial product uses your operator-managed AI Platform credential. End users do not set up Vertex AI, enable Google APIs, or sign in to Google. `livesofia` remains the local voice/session process; a Sofia-controlled remote service holds the shared provider credential and handles the provider connection or obtains a safe short-lived credential when the provider supports one.
- Keep the Sofia pill's existing design and behavior. Every content window visually grows from the pill, and on close collapses into it. Its content fades in *during* expansion and fades out *during* collapse.
- `livesofia` owns the local IPC endpoint. `sofia_ui_layer` is one client of it; other UI programs can subscribe to the same state and register the window kinds they render. MCP tools send window intents through `livesofia`, which chooses a capable UI client.
- `sofia_mcp.db` owns notes, todos, reminders, search, and optional user-configured PostgreSQL sync. The separate `livesofia.db` owns LLM history, memory, and usage. User and model changes use the same MCP-owned revisioned commands; `livesofia` relays `EntityChanged` events so every open view updates immediately. The detailed contract is in [DATA_SYNC_REFERENCE.md](DATA_SYNC_REFERENCE.md).
- Users inspect logs, sessions, tool calls, and detailed turn reports in **`sofia_trace`, a separate GPUI Kit desktop application** with a Langfuse-inspired layout. It subscribes to `livesofia` IPC and can run while the pill UI is closed. `livesofia.db` stores trace metadata, timings, errors, and usage links; full MCP record bodies remain in `sofia_mcp.db`. See [OBSERVABILITY_REPORT.md](OBSERVABILITY_REPORT.md).

## Can the AI Platform key open Gemini 3.8 Live?

**Answer: the model is available, but the exact key route is unverified.** Google lists `gemini-3.8-live` as a Live API model on its cloud platform, and its session guide mentions API key or ADC authentication. However, Google's general Agent Platform authentication page lists API-key support for `generateContent` and `streamGenerateContent`, while the Gemini 3.8 Live developer example uses ADC. Cloud express mode has a distinct key-only endpoint and says Live API access is possible through the API/SDK, yet its published model list does not explicitly show Gemini 3.8 Live. The `gemini-live` Rust crate currently routes its Vertex WebSocket endpoint with bearer tokens and its Gemini API endpoint with an API key. Those sources do not prove that this particular key works with this model on this WebSocket route. [Cloud Gemini 3.8 Live model](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-8-live), [cloud Live session guide](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/start-manage-session), [cloud API-key method limits](https://docs.cloud.google.com/gemini-enterprise-agent-platform/machine-learning/authentication), [express mode overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/start/express-mode/overview), [Rust transport routing](https://docs.rs/gemini-live/0.1.9/gemini_live/transport/index.html).

| Possible credential | Likely route | Status for this plan |
| --- | --- | --- |
| Google AI Studio / Gemini API key | `generativelanguage.googleapis.com` Live WebSocket, `Auth::ApiKey` | Supported by `gemini-live`; verify model access, quota, and whether your key is this type. |
| Google Cloud express-mode AI Platform key | `aiplatform.googleapis.com` express-mode route | Live API is documented for express mode, but Gemini 3.8 Live is not explicit in its model list; test with the real key and endpoint. |
| Standard project API key, including service-account-bound key | Cloud AI Platform endpoint | Do not assume WebSocket authorization; test. Published key support is clear for generation endpoints, less clear for Live. |
| Cloud service-account/ADC bearer token | Regional/global cloud Live WebSocket, `Auth::BearerTokenProvider` | Documented fallback that still requires no *end-user* Google setup when the credential stays on Sofia's service. |

**Connection spike:** identify the credential type without printing the key; use a disposable test credential if possible. Attempt an authenticated WebSocket handshake, send a minimal `gemini-3.8-live` setup requesting audio and transcription, receive `setupComplete`, stream a short test audio clip, and check returned audio, function-call support, and usage metadata. Record endpoint, API version, model resource name, region, HTTP/WebSocket error code, and quota response. Do not mark success from a text `generateContent` call because it exercises a different API. If the key route fails, use the cloud service credential fallback on Sofia's service while retaining the login-free desktop experience.

**Deployment consequence:** a shared, long-lived provider key cannot safely ship inside a Windows/Linux binary or `setting.json`: local users can extract it. Use a Sofia-owned service as the trust boundary. For the first release, proxy bidirectional audio through that service; measure added latency. A provider-issued short-lived client token could later remove the audio hop if supported for the selected endpoint. Google's ephemeral tokens are documented for the **Gemini API** Live WebSocket, not automatically for Cloud AI Platform Live, so test that route separately. Users can avoid Google login while Sofia still issues anonymous installation/session tokens, applies quotas, and prevents one installation from consuming the whole shared quota. [Gemini API ephemeral tokens](https://ai.google.dev/gemini-api/docs/live-api/ephemeral-tokens), [Google API key security guidance](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/start/api-keys).

## Window morph specification

The transition is owned by the UI client. It is a visual promise, not an IPC animation stream. The pill stays where it is and remains recognizable during the effect.

1. On `OpenWindow`, `livesofia` sends the content spec and target size to the chosen UI client. The client gets the pill's anchor rectangle and current display work area.
2. Create the destination surface early with a shell rendered at the pill anchor. Start with pill-like radius/scale and move the visible shell toward its final bounds. For a pill docked on the right, the window grows leftward into the screen. The chosen vertical pivot follows the pill's position: near the top it grows mostly downward, near the bottom mostly upward, and between them it expands both ways. Mirror horizontal behavior when docked left.
3. Mount the real content immediately, clipped to the growing shell. Fade content from transparent to opaque over the expansion, reaching full opacity by the final frame. This avoids a sudden content pop after the window has opened. Keep text interaction and keyboard focus disabled until enough of the window is visible; then enable them at a defined progress threshold.
4. On close, capture any needed window state, fade content down while the shell shrinks toward the pill, then destroy the extra surface only after the morph completes. If an open/close reverses mid-flight, retarget the spring from its current position and opacity.
5. When reduced motion is enabled, use a brief opacity change and immediate final geometry. If the pill is hidden, on another monitor, or its geometry is unknown, use a short local scale/fade from the nearest screen edge.

Use GPUI Kit Base's target-driven `spring` and `transition` channels for size/radius/opacity, with stable IDs per window. Prefer animating a clipped painted shell or temporary transition surface. A genuine OS window moving/resizing smoothly across the desktop is platform-dependent: GPUI's current Wayland layer-surface backend does not expose arbitrary position changes after mapping, so a direct cross-window morph must be prototyped per compositor. This is the highest UI risk. [GPUI Kit motion guide](https://gpui-kit.com/docs/animation/), [GPUI Kit multi-window guide](https://gpui-kit.com/docs/multi-window/), [GPUI 0.3.8 layer-shell options](https://docs.rs/crate/gpui-pre/0.3.8/source/src/platform/layer_shell.rs).

Suggested acceptance checks: open/close from both docked edges and top/middle/bottom pill positions; no flash, content pop, or click-through outside the intended area; correct behavior on multiple monitors and scaling; cancellation/reversal; reduced motion; and a compositor fallback. Tune duration by observed smoothness and input latency rather than hard-coding it in the IPC protocol.

## Local IPC and multiple UI clients

`livesofia` is the authoritative **live-state/UI IPC** event source and command gateway. `sofia_mcp` is the authoritative **user-content** data service and owns its database and content change sequence. `livesofia` routes UI data requests to it, then relays committed content events on the UI stream. `sofia_ui_layer` and replacement clients connect to the same UI protocol. Keep microphone/audio sample processing in `livesofia`; send compressed/rate-limited visualization bins only to clients that subscribe. Local IPC uses Tokio Unix sockets on Linux and Tokio named pipes on Windows. [Tokio Unix listener](https://docs.rs/tokio/latest/tokio/net/struct.UnixListener.html), [Tokio Windows named pipes](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/).

| UI client | Role | What it renders | Priority |
| --- | --- | --- | --- |
| GPUI Kit desktop UI | Primary Windows/Linux client | Pill, morphing content windows, settings, charts, Markdown | First |
| Sofia Trace desktop app | Separate GPUI Kit diagnostics client | Langfuse-inspired sessions, traces, tool calls, logs/errors, detailed reports | Alongside trace instrumentation; read-only trace/data IPC access |
| Alternate native UI | Replace or coexist with GPUI UI | Same state events and typed window specs using another toolkit | Protocol target; implement only if needed |
| CLI/TUI monitor | Diagnostics and accessibility option | Connection, transcript, tool progress, usage, window list | Early, useful for IPC validation |
| Browser-based local dashboard | Optional analytics/settings client | Charts, history, settings through a tightly scoped local adapter | Later; never expose raw IPC or credential to arbitrary webpages |
| Remote/mobile companion | Optional future client | Status/controls and content adapted to small screens | Later; requires a separate authenticated network gateway |
| Automated test client | Contract verifier | Subscribes and asserts state/window lifecycle | Alongside protocol |

These are **UI clients** of `livesofia`. They are distinct from MCP **tool clients/servers**. An MCP server may request `OpenWindow`, but it does not own the authoritative session state or talk directly to a UI process.

The protocol should include `Hello`/version negotiation, client identity and capabilities (`window_kinds`, `markdown`, `charts`, `webview`, `morph`, `max_windows`), `GetSnapshot`, `Subscribe`, `WindowIntent`, `WindowAck`, `WindowClosed`, and state events. A client registers an instance ID; `livesofia` selects one owner for each window by configured preference and capability, stores `window_id -> client_id`, and returns both IDs. Mirror-only clients may subscribe without accepting window intents. On client loss, another compatible client can reconstruct persistent windows from their content specs; ephemeral windows close with a recorded reason. Apply an OS-local peer policy to IPC, per-client capability grants to commands, and a bounded event buffer with snapshot resync on gaps. Do not send provider secrets through IPC.

## Langfuse/LangSmith-style activity reports

The smallest useful set is a session → turn trace → model/tool/retrieval spans, a live timeline, searchable slow/failed tool details, and usage/latency reports in the separate `sofia_trace` app. Its left navigation, center table/timeline, and right detail pane are inspired by [Langfuse's observation model](https://langfuse.com/docs/observability/data-model) and [LangSmith's run/trace/thread model](https://docs.langchain.com/langsmith/observability-concepts). Use Sofia's existing two databases: `livesofia` stores safe trace metadata and canonical usage links, while `sofia_mcp` keeps user content. Show observable tool actions, status, timing, error cause, and linked records; do not claim to display private model reasoning. Full layout, schema, redaction, and test gates: [OBSERVABILITY_REPORT.md](OBSERVABILITY_REPORT.md).

OpenTelemetry is an optional export adapter rather than the local report store. Both [Langfuse](https://langfuse.com/integrations/native/opentelemetry) and [LangSmith](https://docs.langchain.com/langsmith/trace-with-opentelemetry) accept OTLP traces. Remote export must be explicitly configured because prompts, tool arguments, and results can contain private data. The [OpenTelemetry GenAI attributes](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/) document those sensitive fields.

## Recommended next research gates

1. **Provider gate:** OAuth refresh credentials and the Vertex Live WebSocket have now passed a text-input/audio-output test; microphone input, tool calling, and reconnection remain to be tested. See [live model test report](LIVE_MODEL_TEST_REPORT.md). This does not change the end-user no-Google-login requirement for Sofia-managed connections.
2. **Platform motion gate:** build a minimal pill plus one empty morphing shell on Windows and representative Wayland compositors. Resolve window positioning and input region behavior before polishing content.
3. **Protocol gate:** run a GPUI client and a small CLI client against the same `livesofia` IPC server. Confirm snapshot recovery, capability registration, and one-owner window routing.
4. **Crate compatibility gate:** compile the selected audio, MCP, SQLite, and GPUI crates together on Windows MSVC and Linux. Keep optional WebView out until its Linux story is clear.
5. **Visualization gate:** prove declarative Sofia Viz charts, interactive filters, live patches, and a user-controlled 70% translucent panel on Windows and Wayland before evaluating generated Shell scripts or HTML. See [generative visualization research](GENERATIVE_VISUALIZATION_RESEARCH.md).

No provider credential was read, printed, or tested in this research pass.
