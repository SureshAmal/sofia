# Gemini 3.8 Live connection test

Tested: 8 October 2026, from this Linux development workspace.

## Result

The `gemini-live` 0.1.9 crate **successfully connected** to Gemini 3.8 Live through the Vertex AI WebSocket endpoint in `us-central1` using a newly refreshed OAuth access token. The setup completed, a short text prompt produced 142,082 bytes of model audio, and the output transcription was: “Hello, I hope you are having a wonderful day!”

The earlier `.env` value named `VERTEX_AI_ACCESS_TOKEN` was an API-key-shaped value, not an OAuth access token. Passing it as `Auth::BearerToken` failed with “invalid authentication credentials.” It is no longer used by the working probe.

## Working authentication path

`GoogleTokenSource` in [`crates/livesofia/src/oauth.rs`](crates/livesofia/src/oauth.rs) reads `CLIENT_ID`, `CLIENT_SECRET`, and `REFRESH_TOKEN`; sends a form-encoded refresh request to `https://oauth2.googleapis.com/token`; checks the returned bearer token and expiry; caches it; and provides a refreshable `BearerTokenProvider` to `gemini-live`. The model resource includes `PROJECT_ID`, region, and `gemini-3.8-live`. No token or secret is printed by the probe. See [Google's refresh-token procedure](https://developers.google.com/identity/protocols/oauth2/web-server#offline) and [Vertex Live WebSocket authentication](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/start-manage-session).

Run the checks with an ignored `.env` populated from [.env.example](.env.example):

```sh
cargo run -p livesofia --example live_probe -- --token-only
cargo run -p livesofia --example live_probe
```

The probe requests `AUDIO` output and output audio transcription, as required for this native-audio model. [Gemini 3.8 Live model details](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live), [Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities).

The probe now requires **both** audio bytes and transcription text. A follow-up live run produced two text deltas (“Hello, I hope you're ” and “having a great day!”), 132,480 bytes of audio, and the assembled text “Hello, I hope you're having a great day!” The shared UI protocol has `assistant_text_delta` and `assistant_text_final` events, generated by `AssistantTranscript` from `OutputTranscription`. The response card can append deltas immediately and replace them with the final assembled text at turn completion. The local IPC daemon does not yet forward an active provider session into those events.

## What this proves and what remains

This proves refresh-token exchange, Vertex WebSocket authentication, model setup, text input, audio output, and output transcription for this credential/project/region. Function calling, still-image input, and a short streamed video have since passed in the [multimodal probe](LIVE_MULTIMODAL_TEST_REPORT.md). Microphone PCM input, speaker playback, interruption, reconnection after token expiry, and Windows runtime behavior remain untested.

The settings application can collect these credentials, but it should keep secrets in the operating system credential store and store only a reference in `setting.json`. A shared operator refresh token distributed inside a desktop binary or local settings file would be extractable; a Sofia-managed service remains the route for users who should need no Google login or personal credentials.
